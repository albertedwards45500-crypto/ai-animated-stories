## 开场：先用一分钟介绍项目

我做的是一个面向个人创作者的 AI 漫剧生产系统，主要解决剧本、分镜、图片、配音、视频和剪辑分散在不同工具里，制作过程很难复用和追踪的问题。

它把“故事梗概 → 结构化剧本 → 场景和分镜 → 图片、视频、语音素材 → 字幕 → FFmpeg 合成 → 预览下载”串成一条流程。前端使用 Vue 3 和 TypeScript，后端使用 FastAPI，通过 Provider 适配层接入不同 AI 能力。

这个项目的重点不仅是调用模型接口，更是把生成过程做成可查询、可重试、可取消、可追溯的任务系统，同时处理重复调用成本和角色跨镜头一致性问题。目前有本地 Mock 全流程验收记录，也有真实供应商适配代码和历史样片，但还不是经过规模化运营验证的商业产品。

## 1. 说下项目的整体流程

**可以这样回答：**

我会从业务流程和技术执行流程两个角度介绍。

业务上，用户先创建项目和剧集，输入故事梗概，系统生成结构化剧本，再拆成场景、分镜和对白。之后维护角色卡、场景卡和画风，给分镜生成或者上传关键帧、视频和配音，生成或导入字幕，最后用 FFmpeg 合成为可预览、可下载的 MP4。

技术上，生成请求先经过参数校验和业务校验，并检查有没有可复用的成功任务。确实需要调用模型时，再进行真实调用确认和额度检查。后端先把任务以 queued 状态写入数据库，再交给任务执行层处理，接口返回 task_id。

Worker 调用对应 Provider，把进度、结果、错误和输出素材写回数据库。前端通过 SSE 接收任务更新，连接异常时由轮询补充状态。成功后把素材关联到分镜；合成前还会检查素材是否齐全、时长和字幕是否合法。

因此，一次生成既有实际产物，也有完整的任务记录，页面刷新后能够重新查询状态。

**追问准备：**本地 Mock 使用 SQLite 和线程队列；MySQL、Redis、Dramatiq 是项目另一个运行路径，不能把两种模式混为一次验收结果。

## 2. 项目从哪里来？为什么做这个项目？

**可以这样回答：**

这个项目的需求来自个人创作者制作 AI 漫剧时的流程问题。单独让模型写剧本、生成图片或者配音并不难，但把这些能力组合起来时，会碰到素材散乱、角色形象变化、任务失败难追踪、重复生成花钱，以及后期手工剪辑工作量大的问题。

所以我希望做的不是一个单纯的聊天界面，而是一个能够反复使用的创作工作台，把内容、素材、任务和合成结果管理起来。

项目还考虑了本地硬件限制。设计文档里的环境是 RTX 4060、8GB 显存，因此没有把本地运行大型视频模型作为前提，而是让本地承担业务管理、调度和 FFmpeg 合成，通过可替换的 Provider 对接云端模型。

实施顺序是先跑通不消耗模型额度的 Mock 闭环，再逐步验证真实供应商。这样能先把工程问题和模型效果问题分开排查。

**使用提醒：**项目可以表述为个人创作或个人实践需求；没有证据支持“来自企业客户订单”或“已有商业客户”，不要自行补充。

这是一个从需求和设计文档开始逐步落地的个人项目，我主导了需求拆解、技术选型、数据与接口设计，以及前后端、任务链路和验收的推进。开发中使用了 AI 辅助，所以我不会把它描述成每一行代码都完全手写。

## 4. 项目的多层架构、数据接口怎么设计的？

**可以这样回答：**

整体上是前后端分离的单体系统，再把耗时任务交给独立的执行层，没有为了展示技术栈拆成微服务。

前端使用 Vue 3、TypeScript、Vue Router、Pinia、Element Plus 和 Axios，负责项目管理、剧集工作台、素材预览、设置和任务展示。后端 API 层使用 FastAPI 和 Pydantic，处理路由、请求校验和统一响应；services 层集中处理任务状态、剧本解析、角色引用、素材和合成规则；models 层通过 SQLAlchemy 访问数据，Alembic 管理表结构迁移。

AI 能力放在 providers 层，按统一 execute 接口返回结果。文本、图片、视频和语音的供应商差异在这一层消化，任务执行器再把输出转换成项目里的素材和业务数据。

数据关系的主线是“项目 → 剧集 → 场景 → 分镜”。角色卡、场景卡、画风是可复用设定；generation_tasks 管执行过程，generated_assets 管输出文件及其元数据，audio_tracks、subtitles、render_jobs 分别管理配音、字幕和合成。

接口以 REST 为主，比如项目和剧集 CRUD、生成图片或视频、任务查询和重试取消。普通响应统一成 `{code, message, data}`；生成接口返回 task_id，进度单独通过 `/api/generation/tasks/{task_id}/events` 推送。

一个容易混淆的设计是 scenes 和 locations：前者是剧集里的剧情场景，后者是项目级地点设定卡。把两者分开，才能让同一个地点服务于不同剧集和镜头。

**当前实现边界：**这是有分层意图的单体，部分校验和事务逻辑仍在路由及执行器里，不能描述成层次完全隔离的领域架构。

## 5. 为什么用 FastAPI？为什么用 Milvus，而不用 PG？

**先纠正题目与项目的差异：**

我这个项目使用了 FastAPI，但没有使用 Milvus，也没有实现向量检索。业务数据库设计使用 MySQL，本地 Mock 模式使用 SQLite，所以不能套用“为什么用 Milvus 不用 PostgreSQL”的回答。

**关于 FastAPI，可以这样回答：**

选择 FastAPI，主要是因为后端需要整合 Python 的 AI SDK、任务执行和音视频工具，使用同一种语言比较方便。Pydantic 可以描述请求结构和约束，OpenAPI 文档方便前后端联调，也方便实现普通 HTTP 接口和 SSE 进度接口。

不过，FastAPI 本身不会让长时间的视频生成变快。耗时任务仍然需要进入任务执行层，让 API 主要承担受理、查询和控制，避免让用户的 HTTP 请求一直等待模型结果。

**关于数据库，可以这样回答：**

项目主要存项目、剧集、分镜、素材引用、任务状态和费用记录，核心需求是关系查询和事务，MySQL 能满足当前范围。选择它也与已有开发基线和本地环境一致，没有必要为了堆技术引入向量数据库。

如果以后增加“根据语义找相似分镜、角色设定或历史素材”，再根据数据量、过滤需求和运维成本评估向量检索方案。目前没有做过 Milvus 与 PostgreSQL 的实际压测，我不会声称某一种性能更好。

## 7. 做这个项目收获到了什么？

**可以这样回答：**

最大的收获是，我对“调通一个模型接口”和“交付一个能持续使用的系统”的区别有了更具体的认识。

首先，任务状态是业务数据。生成任务耗时长、会失败，也会被取消，不能只靠前端显示一个 loading，而要让状态、重试次数、输入输出和错误信息可查询。

其次，模型能力需要放进明确的工程约束里。剧本要做结构校验，角色引用要记录版本，图片和视频要绑定正确的分镜，素材和字幕不合规就不能进入合成。

第三，我学会了分层验证。Mock 验证流程，离线假响应验证 Provider 请求结构，真实供应商验证接口与效果，媒体工具验证成片是否真的能播放。不同测试回答的问题不同，不能互相替代。

最后，AI 辅助开发让我更重视验收标准。生成代码比较容易，判断它是否满足需求、是否存在竞态、是否会额外消费额度，才是开发者需要承担的责任。

## 8. 做项目遇到了哪些问题？你是怎么解决的？

**建议重点讲前两个，时间充足再补充第三、第四个。**

### 问题一：取消和重试后，旧执行过程仍然可能回写结果

任务提交后在后台运行，用户可能在处理中取消，再重新发起重试。如果只在前端修改展示，旧执行过程返回时仍可能把任务改成成功。

当前代码的处理是：Worker 用带状态和 retry_count 条件的数据库更新领取任务；执行过程中上报进度时重新检查状态和执行轮次；结束时保留取消状态，并拒绝旧轮次覆盖新轮次。渲染任务还要同步对应 render_job 的状态。

相关回归测试覆盖了取消、重试、旧轮次回写和重启恢复。这个处理控制的是应用内状态，不代表一定能撤销已经发给供应商的请求，也不保证取消后供应商不会产生费用。

### 问题二：真实调用确认逻辑让缓存失效，出现重复调用

项目决策记录里有一个很具体的问题：请求不带确认时被确认逻辑拦截，带确认时又绕过了缓存，导致同参数成功结果没被复用。

修正后的顺序是，先去掉 confirm 这类控制字段，按项目、任务类型、供应商、模型和请求参数构造哈希，优先查询成功任务。命中就直接返回已有任务和输出素材，未命中才进入真实调用确认、额度检查和任务创建。

这里也要明确边界：目前实现的是成功结果复用，不能夸大成并发请求下严格的“恰好执行一次”。如果要解决两个相同请求同时首次提交，还需要进一步设计并发去重和原子约束。

### 问题三：供应商的实际协议、模型和音色组合与最初预想不同

图片、视频和语音不是统一格式。有的接口同步返回，有的先返回远端任务 ID 再轮询；语音模型和音色版本不匹配也会失败。项目历史记录中就有这类接入问题。

处理思路是先做最小供应商验证，确认真实请求与响应，再在 Provider 内完成协议适配。业务层只接收统一结果，缺少配置或调用失败时明确报错，不用 Mock 结果冒充真实生成成功。

### 问题四：角色一致性不能只靠重复提示词

项目采用角色卡、主参考图和锁定版本，把角色引用记录进任务。生成分镜关键帧时带入参考图，生成视频时沿用关键帧；角色或引用改变后，旧关键帧不能继续冒用。

这些措施约束了输入和素材关系，但模型仍可能改变脸部、服装或整体画风。历史记录里也出现过动漫关键帧生成视频后向真人风格漂移，所以成片质量仍需要人工复核，不能承诺完全一致。

**本人经历提示：**这些问题有代码、测试或历史决策依据；面试时只把本人实际参与定位和处理的问题说成“我解决的”，其余可以说“项目中出现过，我复盘了处理方式”。

## 9. 项目如果继续优化，你会怎么做？

**可以这样回答：**

我会先按实际风险排序，优先补可靠性和成本控制，再提升内容质量，最后扩展用户能力。

第一，完善任务可靠性。现在任务先落库再投递队列，两个动作之间仍有失败窗口，可以考虑事务 outbox 和补偿投递；同时补并发提交去重、卡住任务的恢复，以及更明确的取消语义。

第二，加强调用成本边界。缓存键应更完整地反映实际模型和配置版本；replay 模式在缓存未命中时也应有明确、可测试的禁止外部调用策略。费用记录需要区分估算与供应商实际账单，避免让用户把内部数字误认为最终扣费。

第三，完善角色版本和质量验收。角色锁定后如果要换形象，需要正式的复制或新版本流程；继续验证参考图策略和供应商效果，建立可重复的画风、人物和镜头样例集，而不是仅靠“看起来还行”。

第四，改进创作体验，比如素材覆盖情况、失败镜头定位、局部重新生成和时间轴编辑。最后，如果确实要开放给外部用户，再增加登录权限、项目隔离、对象存储和部署监控。

这些是后续优化方向，不是当前已经全部完成的功能。当前规模下，我也不会把拆微服务当作默认目标。

**补充后可直接口述：**“我在开发中主要使用【实际 AI 编程工具】，做需求拆解、代码草稿、测试补充和问题分析；业务端接入【实际调用过的模型】，并通过 Provider 把供应商差异隔离。”

## 11. AI 生成代码有 Bug 怎么处理？

**可以这样回答：**

我会按正常的软件排错流程处理，先复现和定位，再让 AI 帮助分析，不会直接把整个项目交给它反复重写。

第一步，固定触发条件，保留请求参数、task_id、日志、数据库状态，以及期望和实际行为。第二步，沿着 API、服务、任务执行器和 Provider 的调用链判断问题在哪一层。

第三步，只围绕根因做小范围修改，再补上能够稳定复现的回归用例。比如缓存命中后是否新增任务、重试之后旧轮次是否还能回写，都比“页面这次看起来成功了”更容易准确验证。

最后，按改动范围验证：后端跑相关测试，前端跑测试和构建，完整流程用 Mock 验收；如果涉及供应商协议，再做单独的真实调用验证，并控制费用。

我会把失败日志和必要代码提供给 AI，而不是把密钥等敏感配置一起贴进去。AI 给出的修复方案需要能解释原因，也不能为了通过测试而削弱业务校验。

我会优先看模型和工具的官方文档、API 说明、更新记录与示例；遇到具体兼容问题，再结合开源仓库、issue 和社区讨论。视频或文章可以帮助发现方向，但接入时还是回到官方协议和自己的最小实验。

对这个项目而言，我更关心它能不能解决具体问题，比如能否携带角色参考图、支持什么模型与音色、接口是同步还是异步、能不能查询任务状态，以及调用成本和生成质量是否合适。

看到一个新能力，我会先在独立验证里测试输入输出、超时和错误行为，确认后再放进 Provider。项目中关于图片协议和语音版本匹配的记录，也说明“看过介绍”和“实际接得进去”是两回事。

**使用前核实：**仓库不能证明本人平时关注了哪些账号、社区或网站，不要编造“长期关注”“第一时间追踪”等个人经历。这里只提供回答结构。

## 13. AI coding 对开发人员有哪些机遇和挑战？

**可以这样回答：**

机遇是它降低了搭建原型和跨技术栈尝试的成本。像这个项目涉及前端、Python 后端、数据库、异步任务和音视频处理，AI 可以辅助生成骨架、接口封装和测试草稿，让个人开发者更快做出可以验证的流程。

挑战是生成速度加快以后，理解、审查和集成的工作并不会消失。AI 可能照着旧协议写接口，也可能遗漏取消竞态、缓存顺序、素材绑定和成本边界；代码能运行，不等于业务结果正确。

还有一个挑战是可解释性。如果开发者自己说不清数据流、状态机和失败后的恢复方式，后续维护就容易被生成代码牵着走。

所以我的理解是，开发者需要更善于把需求变成验收标准、把问题拆成可验证的小块，并对最终结果负责。这个项目里真正值得积累的经验，是识别哪些可以交给 AI 提速，哪些必须自己做判断和验证。

## 14. 用 vibe coding 把项目从需求到做完，整个过程怎样？

**可以这样回答：**

我会把这个过程分成六步。

第一，先明确目标和边界：面向个人创作者，先完成一条短视频生产闭环，不在首版就做多人协作、自动发布或本地大型视频模型。

第二，把需求具体化成 PRD、数据库设计、接口文档和页面流程。比如统一任务状态、定义分镜字段、区分剧情场景和地点卡，先减少 AI 自己补需求的空间。

第三，搭建最小工程，让项目、剧集、场景和分镜的基础数据能创建、保存和展示。按模块推进，每完成一部分就联调和验证。

第四，优先跑 Mock：使用本地测试图、音频和视频，验证任务受理、失败、超时、取消、重试、字幕、合成和下载。这样不用反复消费真实模型额度，也能定位大部分工程问题。

第五，逐个验证真实供应商。先做最小请求，确认协议、参数、模型和输出格式，再加入 Provider。模型效果与稳定性单独评估，不因为 Mock 已通过就默认真实生成质量达标。

第六，做验收和复盘。看测试和构建是否通过，也看 MP4 是否能完整解码、预览是否支持 Range、下载文件是否一致、任务重启后状态是否可查询；遇到问题记录决策和边界，再进入下一轮迭代。

在这个过程中，AI 帮助加快了代码草稿和问题分析，但需求取舍、模块衔接、结果审查和验收仍需要人负责。项目当前完成了本地流程验证，真实模型质量、外部用户和生产部署还需要继续推进，所以我会明确“这一版做完”的范围。
